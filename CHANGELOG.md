# Changelog

## 0.1.9 (2026-10-22)

Overnight flywheel fixes (validation/problems.md P-069, P-071, P-072, P-091), hunted by the chaos and cross-dogfood swarms against the published 0.1.7 and re-verified on the published 0.1.8 before fixing (19 new tests in test/v019.test.ts, 233 total; three pre-existing tests that pinned the old discovery depth bound moved with the bound).

- P-069 REAL: a FIFO (named pipe) planted in the scanned tree hung the scan forever. Surface files were opened with no stat-type check, and opening a FIFO blocks until a writer appears: a pipe at .github/workflows/pipe.yml next to a benign package.json killed the scan in 3 of 3 runs, and the same held for a FIFO at .mcp.json and other surface paths. Every read now stats first and only regular files are ever opened: the central read helpers enforce the check for all discovery and read paths (workflows, package.json, MCP configs, tasks, settings, lefthook and pre-commit configs, plugin hooks), the per surface scanners that stat first keep their isFile checks, and a skipped non-regular file is named in a warning while the benign remainder of the tree is audited normally.
- P-071 REAL: an early-closing reader still received the verdict exit code on a very large report, reporting silent truncation as success (a 35 MB report piped to head -c 100 exited with the verdict code; both sibling tools exit 141). The CLI never adopted the factory flush-aware emit contract written down in FACTORY-NOTES.md: the P-017 fix had replaced process.exit() with process.exitCode, which fixed delivery for cooperative readers, but reports still went out through console.log with no flush callback and no EPIPE handling, so a failed delivery at multi-megabyte size never reached the exit path. Reports (scan and explain, both renderers) now go through a single emit helper that resolves only in the stdout flush callback, exit codes are applied with process.exitCode, and an EPIPE routes to exit 141, matching actionpin and injectcheck. Pipe parity for cooperative readers is byte-identical to v0.1.8 apart from the timestamp.
- P-072 REAL (remainder): nested discovery is no longer bounded at depth 4. The v0.1.8 release closed the silence (bound warning, surface probe just below the bound, no bare CLEAN when surface is detected below it) but the bound itself left realistic monorepo nesting unscanned: a depth 5 package.json dropper floored at REVIEW via the probe and a depth 8 chain verdicted CLEAN with only the warning. The bound is raised to 8, so the depth 5 corpus dropper and depth 8 chains are found and verdict COMPROMISED-PATTERN; the truncation warning and the never-bare-CLEAN rule stay for whatever lies below the new bound. Perf spot checks interleaved against v0.1.8 show no material regression: the 2,000 file tree and a 20,000 step workflow (9.4 MB of report) run at parity, and a synthetic tree of 300 packages at depths 5 to 8 (invisible to v0.1.8) scans in about 0.5 s including the new coverage.
- P-091 REAL: ENV-EXFIL fired on environment inheritance into a child process plus loopback-only network, verdicating CloudCorpRecords/xod COMPROMISED-PATTERN on two windows.yml findings. The scripts build ENV = {**os.environ, ...} and pass it as env= to subprocess for the project's own server and CLI; every network call is loopback to the just-started server, and no credential is serialized anywhere. Exfil analysis now tracks inheritance purity: bulk atoms inside an inheritance expression passed as a subprocess env= (env=os.environ, the {**os.environ, ...} spread, dict(os.environ), os.environ.copy(), and the JavaScript spread and Object.assign forms), and variables tainted only through such atoms, produce a pure flow, and a pure flow fires ENV-EXFIL only when the flow has a non-loopback destination; loopback-only flows produce no ENV-EXFIL. The same forms serialized into a payload (JSON.stringify of the whole env into a fetch body, dict(os.environ) as request data) or paired with a remote destination still fire, and the A1 Shai-Hulud fixture stays COMPROMISED-PATTERN with ENV-EXFIL. The ENV-BULK evidence is honest about the form: inheritance and copy forms are described as bulk access in inheritance or copy form, not as a serialization or dump (the spread form was the gap left by P-020, which covered env=os.environ).

## 0.1.8 (2026-10-22)

Overnight flywheel fix, Wave D (validation/problems.md P-065), hunted against the published 0.1.6 binary in the self-dogfood wave and re-baselined on the published 0.1.7 before fixing (12 new tests in test/waved.test.ts, 214 total).

- P-065 REAL: nested config surfaces were invisible from a parent scan. Discovery was root anchored for every surface except nested package.json files (P-032) and plugin hooks files (P-060): a .claude/settings.json, .vscode/tasks.json, workflow directory, .husky or .githooks directory, lefthook or pre-commit config, or MCP config inside a subdirectory produced no finding from a parent scan and no warning, and a distilled tree holding only nested surfaces scanned CLEAN with total 0 and the empty estate note attached. Discovery is now one bounded recursive walk for every inventoried surface type, reusing the P-032 and P-060 discipline: project directories at most 4 levels below the scan root, at most 200 nested files per surface family with the cap warned, node_modules, .git, dot directories, and symlinked directories never entered. Every surface inventoried at the root is inventoried in a subdirectory within the bound (Claude settings in both the .claude and stow layouts, VS Code tasks, GitHub workflows, husky and githooks files, lefthook and pre-commit configs, MCP configs including .mcp.json, .cursor, .windsurf, and VS Code mcp.json), findings carry their real relative paths, and each surface file is inventoried exactly once however many discovery paths reach it. The report now distinguishes a complete scan from a bounded one: when the walk hits the depth bound with more tree remaining, a warning names the bound and counts the directories just below it that contain hook surfaces, and a scan that is known to have missed surfaces (depth bound, file cap, or unreadable files) never verdicts a bare CLEAN. Verified on the corpus: the waved-nested-config-surfaces fixture now verdicts COMPROMISED-PATTERN with all three worm surfaces RISKY from a parent scan, and a scan of the security-wave workspace from its root now includes the A1 fixture SessionStart and folderOpen hooks. Factory repo scans show no verdict regressions against the Wave D raw outputs; the only total growth is genuine nested surface (greenlight integrations MCP configs, gatefile test fixture lefthook and workflow files).

## 0.1.7 (2026-10-22)

Overnight flywheel fixes, Wave B (validation/problems.md P-060 to P-064), hunted against the published 0.1.5 binary on 10 fresh real repos and re-baselined on the published 0.1.6 before fixing (43 new tests in test/waveb.test.ts, 202 total). The waveb-nested-installer corpus fixture already passed on 0.1.6 through the P-032 fix, so it was out of scope here; the other four Wave B fixtures still reproduced.

- P-060 BLOCKER: Claude Code plugin hook files (hooks/hooks.json) were not scanned at any depth: not at the repo root, not under plugins/<name>/hooks/. A SessionStart curl pipe in that layout scanned CLEAN with total 0 while the identical payload in .claude/settings.json verdicts COMPROMISED-PATTERN. Plugin hook files are now inventoried with the same bounded walk discipline as nested package.json files (plugin root at most 4 levels below the scan root, cap 200 with the cap warned, node_modules, .git, dot directories, and symlinked directories never entered), their hook events (SessionStart, PreToolUse, PostToolUse, Stop, UserPromptSubmit, and the rest of the Claude Code event set) are parsed, and their commands are classified exactly as .claude/settings.json hooks are. The sibling hooks/hooks-cursor.json variant carries the same command object shape under Cursor event names and is inventoried the same way.
- P-061: ENV-EXFIL fired when the credential sat only in an authentication position the v0.1.4 scrubbing did not recognize: custom header names (statsig-api-key, x-api-key with arbitrary names) and headers dictionaries inside one hop Python and TypeScript files (Authorization Bearer templates, f-string Bearer, token f-strings). Authentication position recognition is now shape based: any curl -H header argument whatever its name, any dict entry whose key is an authentication header name, any header shaped entry inside a headers construction (a headers variable, a headers= argument, a headers property), header setter calls, and requests style auth= tuples are authentication positions, and taint no longer propagates through them, so a headers container passed to fetch is not a tainted payload. A credential that reaches a payload position (body, query, URL path, printed output next to a send) still fires ENV-EXFIL, and the A1 bulk env dropper still verdicts COMPROMISED-PATTERN with ENV-EXFIL earned by flow.
- P-062: the token curl (and by symmetry wget) in argument position, naming a package in an install command (pacman -S, apt-get install, brew install, dnf and yum install), counted as NET-FETCH and combined with a credential store write to manufacture ENV-EXFIL on evilmartians/lefthook. Fetch rules now require command position: the fetch binary as the invoked command (the head of a statement or pipeline segment, after sudo and env wrappers, or the head of a command string handed to an interpreter), not any token anywhere in the step. Install lines that genuinely run curl as a later command still fire on that command. The lefthook AUR shape now verdicts REVIEW with WRITE-OUTSIDE and CRED-ACCESS only.
- P-063 (calibration): CURL-PIPE-SH as the only severe evidence, fetching a named vendor installer over HTTPS in a CI workflow step, with no credential and no persistence evidence in the finding, carried COMPROMISED-PATTERN (the uv and opencode installers in the wild). The verdict layer now lands this shape at REVIEW with the finding kept RISKY, under a deliberately narrow test: the finding must be a GitHub workflow run step, CURL-PIPE-SH must be its only severe rule with every rule present part of the pipe shape itself, and the piped URL must be HTTPS and installer shaped (an install, installer, or setup path segment, or a known installer host). Curl pipes on auto-exec hook surfaces, pipes to unversioned or non-vendor sources, and any pipe accompanied by credential access, persistence, or a second severe signal still reach COMPROMISED-PATTERN. Both sides are pinned by tests and the distinction is documented in the README.
- P-064: REMOTE-URL fired on URL string literals that are data in one hop script files (error strings, doc links, docstrings, API base constants), because the P-019 literal awareness did not extend to REMOTE-URL; and DOWNLOAD-EXEC labeled constant inline code (a node -e version comparison, uv run python -c parsers) where nothing is downloaded. REMOTE-URL now matches the URL view for script files: literal contents stay data, except literals handed to network calls, whose URLs are fetch targets and still fire; URLs in workflow shell command arguments keep firing. DOWNLOAD-EXEC now requires an actual download or remote reference inside the evaluated content; constant inline code with no network reference no longer fires it.

## 0.1.6 (2026-10-22)

Overnight flywheel fixes (validation/problems.md P-031 to P-036, P-048, P-049), hunted in Waves A, C, and E against the published 0.1.3 to 0.1.5 binaries, re-baselined on 0.1.5, and fixed test-first (21 new tests in test/flywheel.test.ts, 159 total). Every problem still reproduced on 0.1.5 before the fix.

- P-048: CRLF line endings blinded the workflow parser entirely: every workflow fixture scanned CLEAN with total 0 under CRLF while its LF twin inventoried normally. Workflow text (and the lefthook and pre-commit configs) is now normalized to LF before parsing, and a CRLF workflow produces exactly the verdict, counts, and commands of its LF original.
- P-031: a two hop chain (postinstall runs a benign looking spawner, which spawns the payload) classified the chain head SAFE and verdicted CLEAN, contradicting the documented UNKNOWN or REVIEW floor for chains past the one hop follower. When a referenced local file spawns a further local script, the finding is now floored at UNKNOWN with the second hop named in the evidence. Spawning a plain binary, and benign one hop scripts that spawn nothing, keep their classifications.
- P-032: nested package.json files were not scanned at all (root only, undocumented). Workspace subpackage package.json files are now inventoried like the root one, with referenced files resolved against the nested package's own directory. The walk is bounded and documented in the README: directory depth at most 4 below the root, at most 200 nested files with the cap warned, node_modules, .git, dot directories, and symlinked directories never entered.
- P-049: unreadable files were silently skipped, so a partial scan presented as complete (a mode 000 workflow file vanished and the verdict dropped a tier with warnings empty). Any inventoried file or directory that cannot be read now produces an explicit warning naming it, in the JSON warnings array and the human output, and the verdict is floored at REVIEW whenever any part of the estate could not be read.
- P-033: YAML anchors, aliases, and merge keys understated workflow inventory: an aliased run command was inventoried as the literal alias text, and a merge key step produced no finding at all. Anchors defined in the same file are now resolved: run value aliases resolve to the anchored scalar, alias only steps resolve to the anchored mapping's run value, and merge key steps are inventoried by their resolved content. The anchored definition is inventoried at its use sites, not double counted, and an unresolvable alias is still inventoried at UNKNOWN instead of dropped.
- P-034: .windsurf/mcp.json is now scanned like the other MCP config surfaces.
- P-035: .cursor/mcp.json servers were inventoried twice (once by the cursor surface, once by the generic MCP surface). MCP config files are now inventoried exactly once by the central MCP pass.
- P-036 (documented LIMIT): custom core.hooksPath directories are not scanned; the README limits section now says so explicitly, with the standard .githooks and .husky coverage stated next to it.

## 0.1.5 (2026-10-22)

Re-validation fix found while re-scanning the Round 2 corpus with the published 0.1.4 binary (validation/problems.md P-024). Of the five Round 2 COMPROMISED-PATTERN targets, four cleared under 0.1.4 (langfuse, PostHog/posthog-js, attune-ai, cas). jpoley/flowspec did not: its 10,565 line CLI module still produced ENV-EXFIL, and the driver was hand traced to a false value flow inside the new analysis itself. A keyword argument default tainted the variable name `help` because its prose value mentions the word token ("GitHub token for API requests"), the print disclosure branch then matched a banner printing the word --help, and the send gate accepted the prose word fetch from a docstring as a send construct. The token in that file goes to an Authorization header for the GitHub API and nowhere else; there is no exfil.

- Taint and disclosure now follow code positions only. A variable reference inside a string literal or other data range is a mention, not a use: it cannot propagate taint through an assignment, cannot make a send span tainted, and cannot count as print disclosure. References inside template and f-string interpolation holes are code and still count, and shell echo and printf arguments remain the printed values themselves.
- The print disclosure send gate runs on the code view with data blanked, so a send word appearing only in prose no longer opens the branch.
- Four regression tests in test/round2.test.ts (two flowspec shapes, two controls proving genuine print disclosure still fires in JavaScript and Python); 138 tests total. The flowspec module now classifies REMOTE-URL, ENV-ACCESS, ENV-BULK with no ENV-EXFIL, and the repo verdicts REVIEW.

## 0.1.4 (2026-10-22)

Round 2 real-repo validation fixes (validation/problems.md P-018, P-019, P-020, and the hookcheck half of P-014). Every fix has a regression test built from the Round 2 evidence in test/round2.test.ts (28 tests, 134 total). Measured against the published 0.1.3 binary on the full Round 2 corpus: all 15 findings driving the 5 COMPROMISED-PATTERN verdicts on langfuse, PostHog/posthog-js, attune-ai, cas, and flowspec were hand-read, and none was genuinely exfil shaped; every one was the target repo's own release automation.

- P-018: ENV-EXFIL no longer fires on co-occurrence of a credential shaped name and any URL inside one finding. It now requires the credential value to flow into a send: an env value or a variable assigned from one inside a fetch, axios, requests, http, urlopen, XHR send, or sendBeacon call; an env value in a curl or wget payload, query string, or non Authorization header; a pipeline from an env dump into netcat or a stdin reading curl; or a credential value printed while a send construct is present. A token used as authentication (an Authorization header, the userinfo of a push or clone URL, a --token style flag) is authentication, not exfiltration, and never counts. The verdict layer narrowed with it: credential shaped env references combined with network behavior no longer verdict COMPROMISED-PATTERN on their own. The verdict needs a severe rule, a verified exfil flow, or credential store access (actual credential files) combined with network behavior. One old computeVerdict expectation in test/round1.test.ts that encoded the Round 1 calibration was updated with the Round 2 citation. New rule CRED-EXFIL covers the mirror shape: credential store contents piped or posted straight into a network send.
- P-019: behavior rules (fetch, eval, pipe to interpreter, obfuscation) now match against a code view in script files (JavaScript and Python reached one hop): the contents of string and regex literals are blanked, because defensive tooling quotes the patterns it blocks. Literals handed to exec style calls are spliced back as code, and literals handed to file access calls stay visible to credential path detection, so a real `execSync("curl ... | bash")` and a real `readFileSync("~/.aws/credentials")` still fire. In shell text, echo and printf arguments are treated as output data (a workflow step echoing a JSON test payload into a guard is printing, not executing), unless the pipeline ends in a bare interpreter.
- P-020: env rules match reads, not any mention. The bare os.environ bulk scan now judges the operation that follows each occurrence: .get and subscript reads are named reads, .setdefault and .pop and .update are writes or removals, .copy is a bulk read, and env=os.environ is subprocess inheritance. Shell matches inside `env -u NAME` unset spans and `[ -n "$NAME" ]` existence tests are skipped, and `${#NAME}` is a length, not a value.
- P-014 (hookcheck half): a scan that inventories nothing now carries a note in the report (and therefore in the JSON) stating that nothing was found to audit and the verdict covers an empty estate; the human renderer prints it next to the verdict. A hook-free repo, an empty directory, and a wrong path no longer read as an all-clear.

## 0.1.3 (2026-10-22)

Pipe truncation fix, found during the v0.1.2 re-validation pass. The CLI called process.exit immediately after console.log; stdout to a pipe is asynchronous in Node, so a large JSON report piped to another process truncated at exactly 65,536 characters while the same report redirected to a file was complete (measured on a sparse cli/cli checkout: 145,508 characters to a file, 65,536 through a pipe, JSON unparseable, on the v0.1.2 binary). The scan and explain paths now set process.exitCode and let the runtime flush stdout in full before exiting; exit codes are unchanged. Regression test in test/round1.test.ts: a 350 step workflow report over 64 KiB piped through the real CLI parses in full with the correct exit code. 106 tests total. No classification or verdict changes from 0.1.2.

## 0.1.2 (2026-10-22)

Round 1 real-repo validation fixes (validation/problems.md P-002 to P-007, plus the P-015 and P-016 documentation limits). Every fix has a regression test built from the Round 1 evidence in test/round1.test.ts (26 tests, 105 total). Measured with the published 0.1.0 binary on real repos, real package trees (esbuild, puppeteer), and real agent config repos before the fix.

- P-002 BLOCKER: GitHub workflow block scalar run steps (run: | and run: >, including |- and >- and |+ chomping variants) were not inventoried at all; a repo whose only run step was a block scalar reported total 0, CLEAN. Block bodies are now collected by indentation, dedented, and classified exactly like one line commands, and every workflow finding carries the line number of its run: key.
- P-003 and P-004 calibration: COMPROMISED-PATTERN now requires strong evidence in a single finding: fetched or decoded content executed directly as code (curl or base64 decode piped to an interpreter, eval of fetched content), or credential access combined with network behavior. Weak signals alone (a remote URL, a download by itself, credential access with no send) verdict REVIEW. The canonical legitimate installers esbuild and puppeteer, and the real estates langfuse and cli/cli, no longer verdict COMPROMISED-PATTERN on pattern soup.
- P-004: CRED-ACCESS is matched on content and credential paths, never on substrings of script filenames: a gh-aw step running configure_git_credentials.sh no longer fires it. Comments are stripped before classification (a docs URL in a comment is not a fetch), and a fetch whose every URL is loopback is downgraded (localhost health checks are not network exfil shapes).
- P-005: ENV-ACCESS fires only on credential shaped env names (token, secret, password, api key, and friends, in any access syntax) or bulk access (whole object serialization such as JSON.stringify(process.env), printenv, bare env dumps, whole os.environ use), reported as ENV-ACCESS and ENV-BULK. Ordinary single named reads (NODE_ENV, HOME, RUNNER_DEBUG, ESBUILD_BINARY_PATH, npm_config_user_agent) are not flagged.
- P-006: SHELL-EXEC removed. Being a shell script, or spawning a child process, is the normal state of a hook and no longer escalates a finding to RISKY on its own; a hook is classified by its target script's contents, one hop. A svelte-kit style pre-push running pnpm install, lint, and check is no longer RISKY.
- P-007: Claude settings discovery covers the GNU stow layout (claude/settings.json, no dot, as in real dotfiles repos) and settings nested one level under a config dir (config/.claude/settings.json). A settings path that exists as a directory now produces an explicit warning instead of a silent skip.
- P-015 and P-016 documented in the README limits: .gemini/settings.json is not scanned yet, template configs are inert and not scanned, and UNKNOWN dominance on large real estates is stated with its measured share.

## 0.1.1 (2026-10-21)

Hardening pass. Every fix below was found by an adversarial battery test that failed against 0.1.0 first; the battery lives in test/hardening.test.ts (44 tests, 78 total).

- Fixed crashes on malformed VS Code tasks: a null task entry, or a tasks key that is not an array, aborted the whole scan with a TypeError. Bad entries are now skipped, a non-array tasks key produces a warning, and every other surface still scans.
- Fixed a false positive: a standard pre-commit config with a remote hook repo verdicted COMPROMISED-PATTERN because the bare repo URL matched the remote URL rule. Remote pre-commit repos are now inventoried as UNKNOWN with a note to review the pinned rev.
- Fixed a miss: a UTF-8 BOM in a JSON config made JSON.parse fail and the file was skipped, hiding every hook inside it. BOMs are stripped before parsing.
- Fixed misses in one hop following: a hook that runs `./setup.sh` directly, `node --require ./setup.mjs`, or chains through another package.json script (`postinstall: npm run evil`) now inherits the target classification, the same as `node setup.mjs` did before.
- Fixed a miss: hook files (husky, githooks, agent config files) were classified from only the first 500 characters, so a payload behind padding was invisible. Classification now reads up to 200,000 characters, and referenced local files are read to the same depth.
- Fixed severity: base64 decode piped into a shell (`echo ... | base64 -d | sh`) is now its own rule, DECODE-PIPE-SH, and verdicts COMPROMISED-PATTERN instead of REVIEW. `eval $VAR` without parens now matches the OBFUSCATION rule.
- Fixed rule loss on shell line continuations: `curl ... \` split across lines keeps the CURL-PIPE-SH rule.
- Fixed VS Code folderOpen labeling: runOn is now also read from options.runOptions and from a top level runOn on the task, not only from runOptions.
- Fixed CLI exit codes: scanning a nonexistent path or a file instead of a directory is now a clean error with exit code 2, in both scan and explain. The core scan of a file path returns REVIEW with a not-a-directory warning.
- Shape warnings added: hooks key that is not an object, scripts key that is not an object, and a package.json root that is not an object each produce an explicit warning instead of a silent pass.

## 0.1.0 (2026-10-21)

First release. Security wave, tranche 1.

- `hookcheck scan [path] [--json]`: scans package.json install scripts, Claude Code settings hooks, VS Code folderOpen tasks, husky, lefthook, pre-commit, Cursor and Codex configs, MCP autostart configs, GitHub workflow run steps, and githooks.
- Per hook classification SAFE, RISKY, or UNKNOWN with rule ids and evidence for every finding.
- Verdict CLEAN, REVIEW, or COMPROMISED-PATTERN. COMPROMISED-PATTERN fires when a risky hook fetches remote code or touches credential stores, the Shai-Hulud persistence shape.
- Local file escalation: a hook that runs a local file such as node setup.mjs inherits the classification of that file when the file matches risky rules.
- MCP server with `scan_hooks` and `explain_hook` tools.
- Malformed JSON produces explicit warnings instead of silent skips.
